# Notion 회의록 요약 및 액션 아이템 추출 프로그램 기획서

## 1. 프로젝트 개요

Notion의 특정 페이지에 작성된 회의록을 읽고, 회의 내용을 업무에 바로 활용할 수 있는 구조로 정리하는 프로그램을 만듭니다.

사용자가 Notion 페이지 주소를 입력하면 프로그램이 페이지 내용을 가져와 다음 항목으로 나누어 Markdown 문서로 출력합니다.

1. 회의 전체 요약
2. 현안 및 당면 문제
3. 결정사항과 미결 사항
4. 담당자별 액션 아이템
5. 담당자·기한이 불명확하여 확인이 필요한 항목

## 2. 분석 대상

- 실습 안내 페이지: [Codex 실습.2 - 외부 서비스 연결](https://app.notion.com/p/4093b7f5194a8063977edf66746a1f0a)
- 실제 회의록 하위 페이지: [가을 단풍여행 주간 회의록 (가상)](https://app.notion.com/p/41d3b7f5194a808d8c80c5265bc538c0)
- 확인한 회의록 범위: 2026년 10월 12일~16일의 가상 여행사 주간 회의록

상위 페이지에는 실습 안내와 여러 하위 페이지가 함께 있습니다. 따라서 1차 버전은 **실제 회의록 페이지 주소를 직접 입력하는 방식**으로 만듭니다. 상위 페이지에서 하위 회의록을 자동으로 찾아 선택하는 기능은 후속 기능으로 둡니다.

## 3. 목표 사용자

- Notion에 회의록을 작성하는 소규모 조직 또는 프로젝트 팀
- 회의록에서 담당 업무와 마감일을 빠르게 확인하려는 실무자
- 코딩을 처음 배우는 비전공 대학생

## 4. 핵심 사용 흐름

1. 사용자가 분석할 Notion 페이지 주소를 입력합니다.
2. 프로그램이 프로젝트 루트(`C:\myenv_vibe`)의 `.env`에서 Notion 토큰, 페이지 ID와 OpenAI 설정을 읽습니다.
3. Notion API로 페이지 제목과 본문 블록을 가져옵니다.
4. 표, 목록, 체크박스, 제목, 날짜를 읽기 쉬운 텍스트로 변환합니다.
5. AI가 정해진 출력 형식에 따라 회의 내용을 분석합니다.
6. 분석 결과를 화면에 보여주고 `output/회의록_분석.md`에 저장합니다.
7. 담당자나 기한이 없는 업무는 임의로 추정하지 않고 `확인 필요`로 표시합니다.

## 5. 출력 구조

### 5.1 회의 요약

- 회의 목적
- 핵심 논의 내용 3~5개
- 최종적으로 합의한 운영 방향

### 5.2 현안 및 당면 문제

각 문제를 다음 항목으로 정리합니다.

| 항목 | 설명 |
| --- | --- |
| 문제 | 현재 해결해야 하는 문제 |
| 영향 | 일정, 고객, 비용, 운영에 미치는 영향 |
| 긴급도 | 높음 / 보통 / 낮음 |
| 현재 대응 | 회의에서 정한 대응 또는 검토 중인 방안 |
| 상태 | 결정 / 검토 중 / 미해결 |

긴급도는 회의록에 명시된 표현과 기한을 우선 사용합니다. 근거가 부족하면 `확인 필요`로 표시합니다.

### 5.3 결정사항과 미결 사항

- **결정사항:** 회의에서 확정한 내용만 기록합니다.
- **미결 사항:** 추가 조사, 승인, 확인이 필요한 내용을 기록합니다.
- 제안이나 의견을 결정사항으로 잘못 분류하지 않습니다.

### 5.4 담당자별 액션 아이템

| 담당자 | 소속/역할 | 해야 할 일 | 기한 | 상태 | 근거 |
| --- | --- | --- | --- | --- | --- |
| 별이 | 기획팀 | 전체 예약 분산 결과 확인 | 2026-10-19 | 미완료 | 최종 해야 할 일 |

- 같은 담당자의 업무는 한곳에 모아 보여줍니다.
- 체크된 할 일은 `완료`, 체크되지 않은 할 일은 `미완료`로 표시합니다.
- 담당자, 기한, 상태가 없으면 값을 만들지 않고 `확인 필요`로 표시합니다.
- `근거`에는 해당 업무를 찾은 회의 날짜 또는 구역 이름을 적습니다.

### 5.5 확인 필요 항목

- 담당자가 없는 업무
- 기한이 없는 업무
- 서로 충돌하는 결정사항
- 회의록만으로 완료 여부를 판단할 수 없는 업무
- 표현이 모호하여 사람이 확인해야 하는 내용

## 6. 기능 범위

### 6.1 이번 단계에서 구현할 기능

- Notion 회의록 페이지 주소 입력
- Notion API를 통한 페이지 제목과 본문 읽기
- 제목, 문단, 목록, 체크박스, 표의 텍스트 변환
- 긴 회의록을 여러 부분으로 나누어 분석
- 구조화된 회의 요약 생성
- 현안, 결정사항, 미결 사항 분류
- 담당자, 할 일, 기한, 상태 추출
- Markdown 파일 저장
- 오류 원인을 한국어로 안내

### 6.2 이번 단계에서 제외할 기능

- Notion 원본 페이지 수정
- 액션 아이템을 Notion 데이터베이스에 자동 등록
- Slack, 이메일, 문자 발송
- 여러 회의록을 한 번에 비교하는 기능
- 음성 녹음 파일의 자동 받아쓰기
- 사용자 로그인과 권한 관리
- 상위 페이지의 모든 하위 페이지 자동 분석

## 7. 화면 구성

1차 버전은 설치와 이해가 쉬운 **명령줄 프로그램**으로 만듭니다.

```text
분석할 Notion 회의록 페이지 주소를 입력하세요:
> https://app.notion.com/p/...

회의록을 읽고 있습니다...
분석이 완료되었습니다.
저장 위치: output/회의록_분석.md
```

분석 결과는 터미널에도 표시하되, 긴 내용은 Markdown 파일에서 확인할 수 있게 합니다. 웹 화면은 기본 기능 검증 후 다음 단계에서 검토합니다.

## 8. 기술 구성

| 구분 | 선택 기술 | 용도 |
| --- | --- | --- |
| 개발 언어 | Python 3.11 이상 | 프로그램 실행 |
| Notion 연결 | Notion API | 회의록 페이지 읽기 |
| 내용 분석 | OpenAI API | 요약과 액션 아이템 구조화 |
| 환경변수 | python-dotenv | 비밀정보를 `.env`에서 읽기 |
| HTTP 통신 | requests | Notion API 호출 |
| 결과 형식 | Markdown | 사람이 읽고 복사하기 쉬운 결과 저장 |

최신 API 모델명과 Notion API 버전은 구현 시점에 공식 문서 확인이 필요합니다.

## 9. 파일 구성

```text
08_notion_meeting/
├─ 기획서.md
├─ app.py                  # 실행 시작 파일
├─ notion_reader.py        # Notion 페이지 읽기와 블록 변환
├─ meeting_analyzer.py     # AI 분석 요청과 결과 검증
├─ output_writer.py        # Markdown 결과 저장
├─ requirements.txt        # 필요한 Python 패키지 목록
├─ .env.example            # 루트 .env에 필요한 환경변수 이름 예시
├─ .gitignore              # .env와 결과 파일 제외
└─ output/
   └─ 회의록_분석.md
```

`data/`와 `templates/`가 추가되더라도 원본은 수정하지 않고, 생성 결과는 반드시 `output/`에 저장합니다.

## 10. 환경변수와 보안

프로젝트 루트(`C:\myenv_vibe`)의 `.env`에서 다음 값을 읽습니다.

```text
NOTION_TOKEN=
NOTION_PAGE_ID=
OPENAI_API_KEY=
OPENAI_DEFAULT_MODEL=
```

- 토큰과 API 키를 코드, 기획서, 실행 로그, 오류 메시지에 출력하지 않습니다.
- Notion 연결에는 분석 대상 페이지의 **읽기 권한만** 부여하는 것을 권장합니다.
- 프로그램은 Notion 페이지를 읽기만 하며 수정하거나 삭제하지 않습니다.
- 회의록 전체를 AI API로 전송하므로 실제 개인정보나 기밀정보 사용 전 조직의 보안 기준을 확인해야 합니다.
- 실습에서는 현재 확인한 가상 여행사·가상 직원 데이터만 사용합니다.

## 11. 분석 규칙

1. 회의록에 없는 사실은 만들지 않습니다.
2. 제안, 검토안, 결정사항을 구분합니다.
3. 날짜는 가능하면 `YYYY-MM-DD` 형식으로 통일합니다.
4. 같은 업무가 여러 번 나오면 최신 결정 기준으로 합치되, 내용이 충돌하면 둘 다 남기고 `확인 필요`로 표시합니다.
5. 담당자 이름이 같은 따옴표나 별명으로 반복되어도 같은 사람으로 처리합니다.
6. 체크박스 상태와 문장 표현을 함께 확인하여 완료 여부를 판단합니다.
7. 숫자가 포함된 요약은 원문 수치와 일치하는지 검증합니다.
8. 분석 결과에는 가능한 경우 원문의 회의 날짜나 제목을 근거로 남깁니다.

## 12. 오류 처리

| 상황 | 사용자 안내 |
| --- | --- |
| Notion 페이지 주소가 잘못됨 | 올바른 페이지 주소를 다시 입력하도록 안내 |
| 페이지 접근 권한이 없음 | 해당 페이지에 Integration 연결이 필요하다고 안내 |
| 토큰 또는 API 키가 없음 | `.env`의 변수 이름만 안내하고 값은 출력하지 않음 |
| Notion API 호출 실패 | HTTP 상태와 쉬운 원인을 안내하되 토큰은 숨김 |
| 빈 페이지 | 분석할 회의록 내용이 없다고 안내 |
| AI 응답 형식 오류 | 한 번 다시 요청하고, 계속 실패하면 원문을 보존한 채 종료 |
| 일부 블록을 읽지 못함 | 누락 가능성을 결과 상단에 표시 |
| 결과 파일 이름 충돌 | 기존 파일을 덮어쓰지 않고 실행 시각을 붙여 새로 저장 |

## 13. 운영 및 비용 고려

- Notion API와 OpenAI API의 호출 제한 및 정책은 변경될 수 있으므로 구현 시 최신 공식 문서 확인이 필요합니다.
- 긴 회의록은 AI 입력량이 늘어 비용이 증가할 수 있습니다. 글자 수를 확인하고 여러 부분으로 나눈 뒤 최종 요약하는 방식으로 제한합니다.
- 같은 페이지를 반복 분석할 경우 비용 절감을 위해 페이지 수정 시각과 분석 결과를 연결하는 임시 저장 기능을 후속 검토합니다.
- API 장애 시 원문을 잃지 않도록 Notion 페이지 수정 기능은 사용하지 않습니다.

## 14. 완료 기준

- [ ] 사용자가 실제 회의록 페이지 주소를 입력할 수 있습니다.
- [ ] `.env`의 비밀정보가 화면과 로그에 출력되지 않습니다.
- [ ] 제공된 가상 회의록의 제목, 목록, 체크박스, 표를 읽을 수 있습니다.
- [ ] 결과에 `회의 요약`, `현안 및 당면 문제`, `결정사항`, `미결 사항`, `담당자별 액션 아이템`, `확인 필요 항목`이 구분되어 나옵니다.
- [ ] 제공된 회의록에서 가상 담당자 5명(별이, 구름, 단풍, 나침반, 도토리)의 업무를 구분할 수 있습니다.
- [ ] 담당자 또는 기한이 없는 항목을 추정하지 않고 `확인 필요`로 표시합니다.
- [ ] 원문의 `총 신청 1,240명`, `기존 계획 대비 340명 초과`, `토요일 오전 집중률 46%` 수치가 결과에서 바뀌지 않습니다.
- [ ] 결과가 `output/` 폴더의 새 Markdown 파일로 저장됩니다.
- [ ] 잘못된 주소, 권한 없음, 빈 페이지 상황에서 한국어 오류 안내가 나옵니다.
- [ ] Notion 원본 페이지를 수정하거나 삭제하지 않습니다.

## 15. 테스트 시나리오

### 정상 테스트

1. `가을 단풍여행 주간 회의록 (가상)` 페이지 주소를 입력합니다.
2. 회의 기간과 핵심 수치가 정확히 요약되는지 확인합니다.
3. 다섯 명의 담당자별 업무와 기한이 분리되는지 확인합니다.
4. 결정사항과 미해결 이슈가 섞이지 않는지 확인합니다.
5. Markdown 결과 파일이 `output/`에 생성되는지 확인합니다.

### 예외 테스트

1. 권한이 없는 Notion 페이지 주소를 입력합니다.
2. 일반 웹사이트 주소를 입력합니다.
3. 내용이 없는 Notion 페이지를 입력합니다.
4. `.env`에서 각 환경변수를 하나씩 제외하고 실행합니다.
5. 담당자나 기한이 없는 가상 회의록을 분석합니다.

## 16. 후속 개선 순서

1. **추천:** 기본 명령줄 버전 구현 및 제공된 회의록으로 정확도 검증
2. **추천:** 결과를 사람이 수정할 수 있는 간단한 웹 화면 추가
3. **보류:** 상위 페이지에서 하위 회의록 자동 검색 및 선택
4. **보류:** 액션 아이템을 Notion 데이터베이스에 저장
5. **비추천:** 검토 없이 담당자에게 자동 알림 발송

자동 등록이나 알림은 잘못 추출된 담당자·기한이 실제 업무에 반영될 위험이 있으므로 사람의 확인 절차를 먼저 마련한 뒤 진행합니다.
